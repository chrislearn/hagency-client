# Backend HTTP API parity audit: retained TS vs Rust port

**Bottom line:** of 207 retained HTTP route registrations, 19 are ported and 56 are partial. 124 are missing, 4 return 501 or an explicit "not wired" error (REFUSED), and 4 were changed on purpose with an ADR or spec to cite.

Two things set the picture:
- The Rust service reports `"production_api_parity": false` about itself (`native/hagency/src/lib.rs:457`).
- The project's own migration inventory (`native/fixtures/legacy-inventory.json`) lists all 202 source routes it covers as `port-current-authority` / `parity-unverified`. None is marked as deliberately dropped. So CHANGED-ON-PURPOSE below is used only where a later ADR or spec says so explicitly.

**How the tables are written**
- TS paths are relative to `TS-repo/`. Unless another file is named, the line is in `backend-v2.js`.
- Rust paths are relative to `RS-repo/native/hagency/src/`. The line cited is where the route is registered.
- Rust route prefixes: **op** = `/api/native/v1/...` (operator bearer token, loopback only). **con** = `/console/api/...` (browser session; mutations need a scope). **run** = `/api/native/v1/runner/...` (runner capability).
- **"in-process"** means the retained route was a seam between the backend and the separate Matrix bridge process. Native does that work inside one process, so there is no HTTP route. These are marked PARTIAL only where I found the in-process code. I did not check whether each one is fully wired in production.
- Rust HTTP is served only by salvo `Router::with_path` (`lib.rs:148-165`). MCP runs over stdio and calls the runner API.
