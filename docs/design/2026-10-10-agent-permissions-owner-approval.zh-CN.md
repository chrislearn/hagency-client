# Agent 权限、风险操作与主人审批设计报告

日期：2026-10-10  
状态：设计草案，供评审；未开始本文提出的实现。  
范围：当前 Hagency Desktop、Client OwnerHost，以及原版 hagency-rs 的相关能力对照。

## 1. 结论与目标

当前已经具备主人权限设置、严格的执行授权检查、单次审批，以及 Desktop Service 页面中的审批详情和前台提醒；尚未形成完整的“其他用户请求 Agent → 操作风险判定 → 主人主动收到通知 → 决策 → 执行结果回执”闭环。

用户期望的“安全目录内按权限自动允许；安全目录之外可选择拒绝或请求主人批准”，目前不能完整配置。现有工具／目录白名单未命中时直接拒绝；底层文件能力的越界是硬边界，不能通过批准突破。已有风险字段也不是可配置的风险分类器。

设计目标：让主人明确知道自己的 Agent 可以替谁、在什么资源范围内、执行什么操作；让需要审批的请求可靠到达主人；让每次批准对应可核对的具体操作，并能够区分决定、执行与结果。

本报告只设计这些能力，不开放原生命令、文件修改、MCP，不改运行配置，不迁移现有权限。

## 2. 审计口径与证据

### 3.1 当前策略的实际含义

- 三层按限制合并：任何适用层拒绝，最终拒绝；AskOwner 不覆盖 Deny。
- 未配置的层默认请求允许、工具拒绝。因此只设置 Agent 层为 AskOwner，不能推断工具最终需要审批；另外两层可能仍拒绝。
- AllowWithRules 要求工具名和 canonical_directory 分别出现在两个列表中；未命中直接拒绝，不转 AskOwner。
- 目录字段是能力提案中的规范目录，当前 room-file 提案使用绑定工作区根目录；不能将此字段等同于通用命令实际访问过的全部文件路径。
- `risk` 是适配器提供的标签，不是根据任意命令文本可靠判断风险的系统。
- 请求 AskOwner 针对接受模型请求；工具 AskOwner 针对具体操作。两者是独立授权，界面应明确避免一次批准被理解为放开整段对话。

## 4. 原版哪些值得迁移，哪些仍需重新设计

原版已有：私密审批房间、请求房间状态通知、运行时扩权回调、工作区沙箱与网络限制、精确授权范围、持久授权和撤销、审批应用结果状态。

原版限制：Agent 执行策略主要是 YOLO 开关及授权记录；可复用授权依赖可信运行时提供的精确信息。部分文件／MCP 请求缺少足够信息，不能生成长期授权。不能把原版理解成已有任意操作的风险分类编辑器，也不能把“工作目录在安全目录”当成任意 shell 命令安全的证明。

迁移取舍：复用协议校验、私密投递、授权范围和状态表达的经验；以当前 Server／OwnerHost 归属与设备模型重新接线。避免直接启用 YOLO 或复活一套与当前个人 Agent 并行的授权真相源。

## 5. 建议权限模型

### 5.1 分开四个问题

| 问题 | 设置内容 | 判断位置 |
|---|---|---|
| 谁能请求 Agent？ | 请求者、Room、请求准入策略 | Server 准入与 OwnerHost 执行复核 |
| Agent 已发布哪些能力？ | 文件读写、命令、网络、MCP 等能力门控 | OwnerHost／运行时 |
| 此次操作应如何处理？ | 操作类型、实际资源、规则、未命中策略 | OwnerHost 统一策略判定 |
| 哪些限制不可批准突破？ | 沙箱、执行设备归属、失效绑定、保留资源 | 执行器强制边界 |

发布门控、资源硬边界不是用户审批策略。批准一个请求不能开启未发布的能力，也不能覆盖失效身份或绑定。

### 5.2 三层权限与继承

建议保留 Agent → Room → 请求者三层，增加显式“继承上层”。根层提供默认策略，子层未设置时继承；显式拒绝保持拒绝优先，子层只能在上层授权范围内收紧。

这与当前“缺失层默认工具拒绝”不同，必须版本化迁移：现有显式 Deny 不变，缺失层保留当前有效拒绝语义，主人审阅后才可切换继承。禁止静默将旧配置变宽。

编辑器显示：当前层设置、继承来源、最终有效结果、阻止或要求审批的规则。提供操作模拟预览，但预览不能代替执行前校验。

### 5.3 操作分类与建议默认值

以下是未来设计建议，不是当前已经生效的风险等级。

| 操作 | 建议默认处理 | 可配置范围 |
|---|---|---|
| 已授权工作区内列举／读取普通文件 | 可通过明确启用的只读规则允许 | 根目录、是否含子目录、文件类型 |
| 新建／修改文件 | 请求主人 | 可限定目录和明确写入能力 |
| 删除、覆盖、移动现有文件 | 请求主人 | 展示目标和变化，不与读权限合并 |
| 执行本地命令 | 请求主人 | 可信运行时精确 argv／cwd／权限范围 |
| 访问网络、上传文件、向外发送内容 | 请求主人 | 目的主机／协议／发送内容类别 |
| MCP 操作 | 未知副作用时请求主人；不可表达安全范围时拒绝 | 服务、工具和可验证资源范围 |
| 凭据、系统配置或策略保留资源 | 拒绝 | 不由普通单次批准覆盖 |
| 缺少必要路径／副作用信息 | 不自动放行 | 能完整展示并约束时审批，否则拒绝 |

工具名称、模型声明“低风险”、shell 前缀以及 cwd 单独都不足以建立自动允许规则。长期规则只接受可信适配器能够完整表达并由执行器约束的操作范围。

### 5.4 安全目录与回退策略

建议由主人登记规范化的允许根目录，每条规则绑定操作类型和资源范围；不要采用“工具列表 × 目录列表”的隐式组合。

例如：允许读取 `/Work/agent-data` 及子目录；修改该目录请求主人；访问另一个已登记、可受沙箱约束的目录，未命中规则时请求主人；保留目录永远拒绝。

区分：

- 策略白名单之外、仍在可发布资源边界内：可选择拒绝或请求主人。批准只授予本次明确资源和操作。
- 硬边界之外：直接拒绝。主人须先通过独立配置流程登记新资源；此后重新提出操作，而不是批准原越界请求。

路径判断须覆盖规范化、目录分隔边界、符号链接／硬链接、创建目标的父目录，以及平台特有路径形式。执行前复核，实际 I/O 使用受约束的打开方式，防止批准期间路径替换。任意命令还必须有运行时沙箱限制实际读写和网络；仅检查 cwd 不满足验收。

### 5.5 决策顺序

身份／设备／绑定 → 能力发布门控 → 资源硬边界 → 请求准入 → 三层操作规则 → 精确授权 → 允许／拒绝／生成审批 → 执行前复核 → 执行及回执。

策略规则结果建议使用 Allow、Deny、AskOwner；未命中回退仅提供 Deny 或 AskOwner。规则冲突拒绝优先，有审批要求就不能自动允许。审批期间策略或绑定变化后，重新判定；原请求不再有效则终止，不能沿用旧决定。

## 6. 主人通知与审批闭环

### 6.1 目标流程

1. 其他用户向已授权 Room 中的 Agent 发起请求，保留真实请求者和线程。
2. OwnerHost 对请求或具体工具提案判定；硬拒绝给出可公开的原因，需要审批则持久记录提案并暂停该操作。
3. 使用绑定所确定的真实主人路由私密通知；请求者不能指定审批收件人。原 Room 只显示“等待主人批准”等脱敏状态。
4. Desktop 全局审批入口显示主人名下待审批数量，点击进入完整详情；有权限和能力时发送系统通知，锁屏通知默认隐藏敏感详情。
5. 主人批准／拒绝。通知卡片只是决策入口，不能把普通文本回复解释为批准。
6. 执行设备再次核对主人身份、proposal／digest、有效期、策略版本、绑定代次和能力边界，单次消费决定。
7. 私密审批记录更新决定及执行结果；原 Room 获得适当的脱敏结果。

### 6.2 组件职责

| 组件 | 职责 | 不应承担的职责 |
|---|---|---|
| OwnerHost | 提案、策略判定、决定消费、执行与真实回执 | 不把通知送达当成执行成功 |
| Server／Matrix 投递层 | 主人路由、权限校验、私密投递与脱敏状态中继 | 不批准本地资源、不伪造执行结果 |
| Desktop | 全局列表、详情、通知偏好、明确决策、权限编辑 | 不根据 UI 风险文案自动授权 |
| 运行时／沙箱 | 文件、命令、网络的实际强制约束 | 不依赖模型遵守文字约定 |

### 6.3 通知可靠性与隐私

审批记录和投递 outbox 在 OwnerHost 持久保存，由稳定 proposal ID 幂等投递。私密房间必须验证主人归属和加密条件，验证失败不得退回公共详情投递。

全局未读与待处理状态分离；读过不代表决定。通知可静音，但超时策略不变。重复投递、多个界面操作和过期通知必须汇聚到同一个审批状态。投递失败可以在有效期内重试并明确显示失败，绝不自动允许。

主人离线时保留待审批到截止时间；超时终止等待并留历史。执行设备离线显示不可执行，不能由 Server 代替执行。跨设备审批须新增当前个人 Agent 路径的受认证决定通道；其他主人设备只发送决定，原执行设备保持执行权。设备重新绑定后旧提案失效。

原版私密 Matrix 卡片可作为入口复用，但必须适配当前身份、binding generation、device 与 proposal digest。持久化提案不能恢复已消失的 oneshot；进程重启先把未完成运行协调为中断／结果未知，禁止自动重放工具。重新请求要有新的提案和执行标识。

## 7. 审批详情与状态设计

详情最少显示：Agent 和主人、真实请求者、Room／线程、请求目的、审批类型（接受请求或执行工具）、精确操作、实际路径／网络目标、写入差异或内容预览、命中规则与原因、审批范围、截止时间及执行设备状态。

内容可能包含机密；默认安全摘要，主人按需展开完整参数。原 Room 和系统通知不携带完整本地路径、命令、文件内容或凭据。完整参数中的敏感字段需要可解释的遮盖，摘要必须绑定未遮盖原提案的 digest。

状态分成三个独立维度：

| 维度 | 状态示例 | 含义 |
|---|---|---|
| 决策 | 待审批、批准、拒绝、过期、取消 | 主人的决定或等待终止 |
| 投递 | 待发送、已送达、失败、已读 | 消息可见性，不是授权 |
| 执行 | 未开始、执行中、成功、失败、结果未知、中断 | 真实运行结果 |

批准后不能直接显示“已完成”。发送超时显示“决定送达未确认”，通过查询对账恢复；不要由 UI 再提交一个新的授权。运行时未提供可验证回执时保留结果未知。

## 8. 持久授权与撤销

建议先做单次可靠闭环，再增加“本任务”和“长期”授权。任务授权绑定任务代次；长期授权绑定主人、Agent、资源范围、精确操作、执行环境与权限版本，可设置期限。

详情页必须展示实际授权范围；信息不足的文件或 MCP 操作只允许单次，不提供“始终允许”。撤销和策略收紧在后续操作前生效，已消费决定不能复用。撤销不能声称回滚已发生的外部副作用；运行中的停止结果单独记录。

## 9. 建议实施顺序与交付边界

| 阶段 | 工作 | 完成标准 |
|---|---|---|
| P0：可解释的当前设置 | 最终策略、缺失层默认说明、拒绝／审批原因、发布能力说明 | 主人能预测一项操作为何被拒绝或审批，不改默认权限 |
| P1：可靠审批闭环 | 持久记录、outbox、私密投递、全局列表、单次决定对账、重启协调 | 不必停留在 Service；重复、离线、过期、重启均无自动放行或重放 |
| P2：细分操作与目录规则 | 结构化资源、逐规则目录、读写分类、未命中策略、继承版本迁移 | 安全目录内外、子目录与硬边界语义可配置且真实强制执行 |
| P3：执行回执与授权管理 | 执行状态、历史、本任务／长期授权、撤销 | 主人能核对实际效果，并控制可复用授权 |

P1 先采用现有可触发的模型请求审批验证整条通知链路，不为演示而提前开放原生命令。P2 应先实现发布能力中的结构化文件操作；命令／MCP 必须单独通过适配器与沙箱资格验证后再发布。

## 10. 测试与验收计划

以下为待执行计划，本报告未运行这些新测试。

| 场景 | 预期结果 |
|---|---|
| Bob 请求 Alice 的 Agent | 私密详情只路由 Alice；Bob 仅获得脱敏状态 |
| 错主人／错设备／错 Agent／错 Room／旧 binding generation | 拒绝决定，不执行 |
| 改参数／digest 不匹配／重放／并发批准和拒绝 | 不产生第二次执行，只有一个有效终态 |
| 主人切到其他页面／其他 Room | 全局待审批可见，无详情泄露 |
| 主人离线／通知失败／执行设备离线 | 明确可见状态，截止前可重试投递，绝不自动批准 |
| 过期通知被点击 | 显示过期，不恢复旧执行 |
| 接受模型请求后出现写文件操作 | 重新按工具策略判定，不能沿用请求批准 |
| 某一层 Deny、另一层 AskOwner | 拒绝，并显示阻止层 |
| 旧缺失层配置迁移 | 保留既有拒绝结果，不静默扩权 |
| 白名单内只读、同目录写入、可审批范围外访问 | 分别得到所配置结果；写权限不由读权限推导 |
| 硬边界越界、符号链接逃逸、目录前缀碰撞、路径替换 | 拒绝或由受约束 I/O 阻止，无未授权访问 |
| cwd 合法但命令访问其他目录或联网 | 实际沙箱约束生效，不能只通过 cwd 检查 |
| 等待审批期间策略收紧／退 Room／重新绑定 | 原提案不能继续执行 |
| 决定已提交但响应丢失 | 对账同一决定，不创建新授权 |
| 重启时正在等待或执行 | 不自动恢复工具；中断／未知状态真实保留 |
| 长期授权撤销／任务代次变化／执行环境变化 | 旧授权不匹配后续操作 |
| 凭据／文件内容出现在参数中 | 私密详情适当遮盖，公共及锁屏无敏感数据 |

验证层次：策略单元测试 → OwnerHost／Server 协议集成 → Desktop 注册组件测试 → 真实 Alice/Bob 两账户私密投递与决策 → 真实运行时边界验证 → 离线／重启／重复消息故障验证。通过一个层次不能替代后续端到端验收。

## 11. 待产品评审的选择与建议

- 首个通知通道：建议主人私密 Matrix 房间＋Desktop 全局入口；系统通知只作为提醒，入口重新取最新状态。
- 多设备范围：建议先允许主人已认证设备查看和单次决策，只有原执行设备消费；不得允许任意已登录设备接管执行。
- 目录外访问：建议默认拒绝；主人明确设置为 AskOwner 时，只适用于已登记、可强制约束的资源范围。
- 审批时限：现有多数提案为五分钟；第一阶段保持现有有效期约束，后续若允许配置，须与执行期限、队列上限和通知重试统一设计。
- 默认权限：保留当前受限行为；推荐规则通过向导显式启用，不随升级自动开放。
- 历史与私密详情保留期：应提供删除／保留设置；持久化加密、访问审计和私密字段处理须在 P1 定义，不收集无关文件内容。

这些是建议取舍，不是本轮已批准或已实施的产品配置。
