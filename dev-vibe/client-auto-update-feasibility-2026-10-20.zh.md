# Hagency Client 自动更新可行性与工作量

日期：2026-10-20。源码基线：`f5f62ffbff6f8567de9d1a7318134289c2a43a9c`。

Client 可以实现检查更新、后台下载和安装重启。检查和下载难度较低；可靠安装需要适配操作系统、发布签名、Agent 停机和失败恢复。建议第一版采用自动检查、可选自动下载、用户点击重启安装，运行中的 Agent 任务会延后安装。

按一名熟悉项目的开发者投入估算，Windows 完整闭环约 5–8 人日，Windows、macOS 和 Linux AppImage 约 10–15 人日。后者包含跨平台安装升级验证；证书办理和外部审批等待另计。以下是工程估算，尚未通过更新原型验证兼容性。

## 推荐实现

优先验证 `cargo-packager-updater`，沿用现有打包工具。官方提供独立 Rust API、更新签名验证、下载和安装接口，不需要换用 Tauri 或 Electron。[Packager 官方说明](https://docs.crabnebula.dev/packager/updater/)

更新服务提供检查、下载、待安装、准备退出、安装失败等状态；网络和签名处理在后台线程执行。该库 API 是同步接口，不能在 Makepad UI 线程直接调用。下载与安装接口可以分开，适合后台下载后等待用户安装；下载 API 返回内存字节，持久暂存、下载大小限制和重启后再次验证仍需要应用封装。[Update API](https://docs.rs/cargo-packager-updater/0.2.3/cargo_packager_updater/struct.Update.html)

首版使用全量更新；更新清单包含版本、发布日期、说明及各平台附件 URL、格式和签名。CI 从同一源码生成安装包与清单，在所有目标、摘要和签名校验通过后发布。附件 URL 固定到版本，客户端按语义版本比较，正式通道排除预发布版本和降级。开发构建及嵌入 OctoSense 的模块禁用独立安装。

清单可以作为 GitHub Releases 静态附件，例如 `latest.json`，客户端通过 `releases/latest/download/latest.json` 获取，无需首版增加 Cloud 数据库或业务接口。面向中国网络的可达性需实测；若 GitHub 下载不稳定，可再接同源站点或 CDN 镜像。镜像使用同一签名校验，客户端不需要携带 GitHub 凭据。

### 各平台安装策略

| 平台 | 推荐处理 | 主要验证点 |
| --- | --- | --- |
| Windows x64 | 下载并验证 NSIS 安装包；完成退出准备后启动安装器，再启动新版本 | 当前用户和机器级安装、UAC 取消、文件占用、托盘与单实例锁、重启后的权限 |
| macOS Intel 与 Apple Silicon | 保留 DMG 首次安装，新增完整 `.app.tar.gz` 更新附件 | 签名公证后的完整 App、安装目录权限、从 DMG 运行时引导安装、重启 |
| Linux AppImage x64 与 ARM64 | 验证下载包后替换外层 AppImage | 外层路径、执行权限、目录可写性、替换失败保留旧文件 |
| Linux DEB 与 AUR | 检查版本并提示通过相应包管理方式升级 | 不让普通 GUI 越过包管理器直接覆盖系统文件；仅安装 DEB 不等于已有 APT 更新源 |

候选库支持的安装格式是 app、appimage、nsis、wix；DMG 和 DEB 不在这组自动安装格式中。清单平台键应以实际库实现为准，官方示例存在 macOS 键名差异，原型中固定验证。[库格式与清单说明](https://docs.rs/cargo-packager-updater/latest/cargo_packager_updater/)

### 安装前退出屏障

现有 `handle_shutdown` 会最多等待 15 秒停止当前 Agent owner，超时只记录错误后继续退出。更新需要增加一个可确认结果的准备步骤：停止接受新任务，保存草稿与运行状态，停止并确认受管进程释放文件，超时则取消本次安装并显示原因。不得承诺任务在新版本中自动接续，除非另外实现和验证。

特别注意：候选库 0.2.3 的 Windows 安装分支启动安装器后直接调用 `std::process::exit(0)`。如果从 UI 按钮直接调用，会绕过 Makepad 的 Shutdown 事件及清理。因此必须在调用安装接口前完成退出准备；若库行为妨碍可靠交接，再用独立更新 helper 封装。安装失败后的恢复也需纳入这个流程。[候选库源码](https://docs.rs/cargo-packager-updater/0.2.3/src/cargo_packager_updater/lib.rs.html)

### 签名与恢复边界

更新包签名用于确认下载内容由发布方产生，需要一次性生成密钥、保护 CI 私钥、在客户端内置公钥。它与 Windows Authenticode、Apple Developer ID 属于不同机制；SHA256SUMS 不能替代内置公钥的真实性校验。现有 secrets 上传脚本使用的历史变量名与当前官方文档变量名不同，实施时按选定 packager 版本统一核对，不直接照搬。

首版包含下载失败重试、损坏包拒绝、安装前取消及可手动重新安装的恢复入口。系统签名证书未就绪时可开发测试更新功能，但正式发布需分别验收系统提示和权限行为；不能承诺所有机器均完全静默。

自动回滚应独立排期。`hagency-store/src/database.rs` 拒绝高于当前支持版本的数据库，当前 domain schema 为 60；新版本迁移数据后，简单换回旧 EXE 可能无法打开数据。涉及本地数据库、Matrix 状态和账本的一致回滚，需要兼容策略及经过验证的备份恢复，不能宣称更新库已经解决。

下表按累计可交付范围估算，行与行不相加。一人日按约 8 小时有效工程投入计算。

| 手动检查与提示下载 | 0.5–1.5 人日 | 版本比较、错误状态、更新说明、打开正确下载入口 |
| 自动检查与后台下载 | 3–4 人日 | 设置、频率控制、下载进度、签名验证、暂存；用户仍可手动安装 |
| Windows 安装重启闭环 | 5–8 人日 | 上述能力、发布清单与签名、Agent 退出屏障、安装器交接和真实升级验证 |
| Windows 加 macOS 加 Linux AppImage | 10–15 人日 | 五个目标验证、macOS 专用附件、AppImage 替换、DEB 提示升级、故障回归 |
| 增加灰度与多通道、差分、自动数据回滚 | 20–30 人日起 | 需重新细化产品要求和服务端范围；不计入首版 |

## 建议首版范围与验收

首版提供手动检查、启动后延迟检查、可选后台全量下载、更新说明、稍后安装与立即重启安装。自动检查失败保持安静，手动检查显示失败原因；后台有任务时延后安装，普通关闭到托盘不触发安装。先完成 Windows N 到 N+1 原型，再扩展到其余目标。

至少验证：同版本和较新开发版本不降级、正式通道不误装预发布、架构匹配、清单或签名异常拒绝、下载中断和磁盘不足、UAC 取消、AppImage 目录只读、任务退出超时、安装路径含空格、账号和聊天数据保留、Octos 与资源一起升级、安装后版本正确且仅运行一个实例。

已经安装的旧版本没有 updater，需要用户先手动安装一次带此功能的版本，之后才能自动升级。当前产品名、publisher 与历史 Desktop 包存在变化，原型还要验证是否识别为同一个安装，不能仅凭 identifier 保持不变便假定历史升级无缝。

## 考察范围

本轮完成源码、记忆、打包配置与上游文档考察，仅新增评估和记忆文档；没有修改业务代码、编译、安装、读取实际 secrets、生成密钥或发布版本。已有正式发布阻塞维持原状态，本次可行性评估不构成发布授权。

后备方案为 Velopack，其官方 Rust SDK 支持跨平台检查、下载和重启更新，但需要调整现有打包与应用启动入口；现阶段优先验证与现有 cargo-packager 配套的库。[Velopack Rust 文档](https://docs.velopack.io/getting-started/rust)
